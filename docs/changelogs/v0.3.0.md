# v0.3.0 technical changelog

The [public release note](../releases/v0.3.0.md) summarizes the first official
release. This changelog records the final changes made after beta.5 and the
validation used to promote protocol v3 to stable.

## Context and root causes

- Renderer child processes received chart paths through environment variables.
  Windows could damage non-ASCII chart or variant text before Lua read it,
  making a valid custom chart fail only when launched for Online playback.
- Game modifiers were local preferences. A host could describe room rules but
  could not make every player run the same speed, VFX, tap, side, barely, and
  restart settings. Older protocol-v3 peers also had no capability signal that
  proved they could apply a policy.
- The release metadata validator required an `alpha` or `beta` suffix even
  though the publication workflow already distinguished stable tags from
  prerelease tags.
- The companion lockfile referenced `event-listener` 5.4.1 after a RustSec
  advisory made the previously green dependency graph fail the hosted audit.

## Implementation details

### UTF-8-safe chart launch

- The Rust launcher transports chart and variant values as ASCII hexadecimal
  environment fields. The Lua renderer validates and decodes those fields,
  retaining the legacy raw variables as a compatibility fallback.
- Tests cover non-ASCII chart and variant names across the child-process
  boundary and the canonical autoplay Lua path.

### Host-enforced modifiers

- `RoomModifiers` is native room state with validated speed and Boolean VFX,
  Taps, Sides, Barelies, and Restart On fields. Only the host can change it,
  and changes freeze during countdown and play.
- Authentication advertises modifier-enforcement support. A current room
  rejects an older protocol-v3 runtime instead of allowing a peer that would
  silently ignore host policy.
- The launch path applies the authoritative room values after native state is
  transferred to Beatblock. The Lua adapter temporarily swaps the relevant
  settings, prevents enforced values from overwriting the local save, and
  restores the player's preferences when Online initializes again.
- Settings presents editable modifier controls to the host and the same values
  read-only to participants. Protocol snapshots keep the field optional so
  historical persisted data remains readable; live authentication closes the
  downgrade path.

### Stable release and dependency policy

- Package, Rust, Lua, packaging, UI-fixture, documentation, and archive names
  now use `0.3.0`. Release-contract tests accept stable semantic versions while
  retaining alpha/beta coverage and exact tag-to-package matching.
- The tag workflow continues adding `--prerelease` only when the tag contains
  a hyphen, so `v0.3.0` publishes as a normal GitHub Release.
- `event-listener` was updated from 5.4.1 to 5.4.2 within the existing Slint/
  zbus dependency constraints. The Windows product graph and hosted RustSec
  audit use the patched version.

## Migration and compatibility

All machines in a room should install `v0.3.0`. An older protocol-v3 runtime
may be rejected during authentication because it cannot prove modifier-policy
support. This is deliberate; it prevents a race from starting with different
effective gameplay rules.

The wire protocol remains version 3. Historical snapshots without a modifiers
object use defaults, while active current peers must pass the capability
challenge. The verified Beatblock baseline remains
`1.7.1a (Early Access)[d40b7083]`; newer structurally valid builds may be
accepted but are not thereby verified.

Close Beatblock and OBS before installer or OBS-component mutations. Existing
OBS Player Stream items are video-only; add the desired independent Online
audio source and validate its route after upgrading.

## Known limitations

- The installer remains unsigned. Checksums and GitHub attestations establish
  integrity and workflow provenance but do not prevent the Windows **Unknown
  publisher** warning.
- Physical OBS 32.1.2 color accuracy, independent audio routing,
  process-loopback behavior after desktop mute, A/V alignment, and long-run
  drift depend on the event machine and remain tracked in issue #28.
- Direct-IP hosting requires a reachable UDP port or an operator-provided VPN/
  proxy. The project does not provide accounts, matchmaking, a public room
  browser, or a hosted relay.
- Later Beatblock builds and each production network/OBS environment still
  require their own compatibility and event rehearsal.
