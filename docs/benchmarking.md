# Benchmarks, stress gates, and trials

Run `pnpm test:stress`, `pnpm benchmark`, or `pnpm trial` from a developer checkout. Release users do not run these commands.

The Rust suite covers scoring results, duplicates/gaps, DNF/set totals, setlist advancement, admission authority, role capacity, authenticated reconnect identity, SPAKE2/QUIC exchange, renderer datagrams, safe restart-to-Offline behavior, atomic exports, installer/OBS transactions, selected arbitrary/Unicode targets, missing or corrupt payload detection, monotonic progress, Lovely-module inventory conformance, protocol-v1 rejection, and Lua compilation using Beatblock's own `lua51.dll`. The pure dashboard model is also executed by that runtime to verify phase selection, role permissions, primary-action precedence, eight-row scrolling, focus transitions, and contextual Help.

`companion/examples/host_room_trial.rs` writes a 16-player/32-spectator machine-readable simulation. The benchmark records chart cache, completed coalesced export publication (not just queue latency), buffered NDJSON journals, batched SQLite journals, recovery counts, and direct-room throughput. The runtime lifecycle gate verifies lazy hidden execution, mutex enforcement, explicit shutdown, parent cleanup, and the 30 MB idle working-set target. `scripts/run-trials.mjs` produces `full-capability-latest.json` and `.md` without requiring pnpm's workspace wrapper.

The automated aggregate currently lives in [`full-capability-latest.md`](../reports/trial-runs/full-capability-latest.md). The separate [`injected-installer-lifecycle-latest.md`](../reports/trial-runs/injected-installer-lifecycle-latest.md) records the physical `.test` flow from the packaged installer payload: normal game launch, lazy Online startup, token-protected API telemetry, main-menu return, and runtime/API shutdown.

The latest arbitrary-folder installer recovery is [`installer-reliability-latest.md`](../reports/trial-runs/installer-reliability-latest.md). It records the isolated `.test\Beatblock` missing-dashboard recovery, the generic-helper-error reproduction, exact firewall-path diagnosis, Windows path normalization, elevation-wording regression, helper status-file trial, and the remaining secure-desktop approval gate.

Blocking automated targets are ranking update p95 below 250 ms under the modeled 100 ms path, average gameplay telemetry below 15 KiB/s/player excluding transfers, complete journal recovery, and exact result agreement.

Physical claims require physical evidence. The trial sheets under `docs/trials` cover public WAN/port mapping, four 720p60 renderers for ten minutes, OBS 32.x audio/video and reassignment, and clean-machine Windows install/Steam launch/repair/uninstall. The installer/source-load gate currently passes on OBS Studio 32.0.4 x64; renderer video and audio synchronization remain separate gates. Record hardware, OS, timing, bandwidth, frame drops, skew, screenshots, and every fallback. A simulation must never be labeled as a completed physical gate.

The latest UI captures are [`dashboard-room-latest.png`](../reports/trial-runs/dashboard-room-latest.png), [`dashboard-connect-latest.png`](../reports/trial-runs/dashboard-connect-latest.png), [`dashboard-mismatch-latest.png`](../reports/trial-runs/dashboard-mismatch-latest.png), and [`dashboard-help-latest.png`](../reports/trial-runs/dashboard-help-latest.png). They execute the shipped Lua state/model with the reference Beatblock pixel fonts, palette mapping, and 600x360 logical canvas rather than reproducing the interface in HTML.

## Recommended system and network specifications

These recommendations cover BBT's incremental load. Beatblock, custom charts, other mods, OBS scenes, encoders, browser sources, and simultaneous local streaming can require additional capacity.

| Profile                                    | CPU                          | System memory  | GPU                                                                                                | Disk                 | Network                                                                    |
| ------------------------------------------ | ---------------------------- | -------------- | -------------------------------------------------------------------------------------------------- | -------------------- | -------------------------------------------------------------------------- |
| Player or spectator                        | Modern 4-core/8-thread x64   | 8 GiB          | Integrated or dedicated GPU that already sustains Beatblock's target frame rate                    | SSD, 1 GiB free      | 5 Mbps down / 1 Mbps up                                                    |
| Room host, no renderer slots               | Modern 6-core/12-thread x64  | 16 GiB         | GPU that already sustains Beatblock's target frame rate                                            | SSD, 1 GiB free      | 250 Mbps upload at 48 participants; about 10 Mbps upload at 8 participants |
| Broadcast host, four 1280x720 60 fps slots | Modern 8-core/16-thread x64  | 32 GiB         | Dedicated GPU, 8 GiB VRAM, with OBS and Beatblock below 80% utilization before renderer assignment | SSD, 2 GiB free      | Room-host upload above, plus the encoder/streaming destination requirement |
| Experimental four 1920x1080 60 fps slots   | Modern 12-core/24-thread x64 | 32 GiB or more | High-end dedicated GPU, 12 GiB VRAM or more                                                        | NVMe SSD, 2 GiB free | Same as the broadcast host                                                 |

Four 1080p60 slots are not a baseline-supported broadcast target: they process 2.25 times as many pixels as the four-renderer 720p60 trial. Prefer 720p, 30 fps, Clean mode, or fewer assigned slots if frame drops or host frame-time regression appears. CPU model names are deliberately omitted because per-core speed, chart complexity, other mods, OBS encoding, and thermal limits matter more than a product generation label.

### Basis for the estimates

The following values are measured by the automated suite or calculated directly from fixed wire and buffer layouts. They are floors, not whole-machine utilization predictions:

| Resource                   | Evidence                                                                                                                                                                                                                                                                                                                                                                                                  | Budget implication                                                                                                                                                                                                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Runtime CPU                | The latest benchmark sustains more than 300,000 batched SQLite journal events/s and more than 700,000 buffered NDJSON events/s; room publication is capped at 20 Hz, SQLite batches at 25 ms, journal flushes at 50 ms, and exports/chart checks at 100 ms.                                                                                                                                               | The runtime is not expected to be the CPU bottleneck. Renderer game processes and OBS determine the broadcast-host CPU requirement.                                                                                                                                            |
| Runtime memory             | The lifecycle gate measures about 16 MiB idle working set and fails above 30 MiB.                                                                                                                                                                                                                                                                                                                         | Reserve 30 MiB for the runtime. The 8/16/32 GiB recommendations provide room for Beatblock, renderer children, OBS, charts, and the OS.                                                                                                                                        |
| Frame-ring memory          | Each slot maps three 1920x1080x4-byte buffers plus a 64-byte header: 23.73 MiB. Four slots map 94.92 MiB.                                                                                                                                                                                                                                                                                                 | Reserve 95 MiB of addressable system memory and backing-file space even when output is 720p.                                                                                                                                                                                   |
| GPU/copy bandwidth         | One 720p RGBA frame is 3.516 MiB. A 60 fps slot therefore moves at least 210.94 MiB/s; four slots move 843.75 MiB/s. Four 1080p60 slots move 1,898.44 MiB/s.                                                                                                                                                                                                                                              | These are minimum readback/copy rates before OBS copies, texture upload, composition, and encoding. Validate drops and GPU utilization on the actual driver and encoder.                                                                                                       |
| Code-visible video buffers | Two renderer output canvases plus one OBS texture are about 10.55 MiB/slot at 720p and 23.73 MiB/slot at 1080p.                                                                                                                                                                                                                                                                                           | Four slots expose at least 42.19 MiB or 94.92 MiB of pixel buffers respectively, excluding game assets, source canvases, driver staging, encoder surfaces, and duplicated process resources. This is why practical VRAM headroom is much larger than the visible buffer floor. |
| Gameplay telemetry         | A packed render sample is 32 bytes at 60 Hz, or 1.875 KiB/s (0.0154 Mbps) per active player before transport overhead.                                                                                                                                                                                                                                                                                    | Player upload is small; the 1 Mbps recommendation leaves ample control/journal headroom.                                                                                                                                                                                       |
| Room snapshots             | A representative maximum room built from the current `RoomSnapshot` schema, 16 players, 32 spectators, and a five-chart setlist serializes to about 21 KiB. At the 20 Hz publication cap this is about 3.4 Mbps delivered to one peer and 160.6 Mbps of host payload fan-out to 47 remote peers, before QUIC/IP overhead. The same model with eight total participants is about 5.8 Mbps of host fan-out. | Recommend 5 Mbps client download and 250 Mbps host upload for a maximum room. The 10 Mbps small-room recommendation should be treated as a minimum rather than a guarantee.                                                                                                    |
| Persistent disk            | Runtime binary plus installer is about 51 MiB. The four frame rings reserve 94.92 MiB; logs are capped at 64 MiB and chart cache at 128 MiB. Journals retain 30 days.                                                                                                                                                                                                                                     | The known bounded footprint is about 339 MiB before the database, journals, match history, charts, OBS, and temporary installer space. Recommend 1 GiB free normally and 2 GiB for broadcast hosts.                                                                            |
| Export writes              | The benchmark coalesces 250 requested snapshots into no more than 60 physical publications and currently writes about 8 KiB of export content.                                                                                                                                                                                                                                                            | Text exports are metadata-latency sensitive rather than throughput heavy. Use an SSD; physical frame-map writeback and chart hashing remain OS- and hardware-dependent.                                                                                                        |

The network figure is a code-derived worst-case estimate, not a completed WAN measurement. Session identifiers, display names, setlist length, transport framing, loss, retransmission, and publication frequency change the result. Record actual process CPU, GPU engine utilization, dedicated/shared GPU memory, working set, disk bytes/s, and interface bytes/s during the physical trials.
